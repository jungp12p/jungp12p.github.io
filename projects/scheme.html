Scheme Interpreter in C: from Parentheses to Closures

This project builds a full interpreter pipeline in C: lexical analysis, parsing, evaluation, and printing. It also highlights one of the most important systems topics in C: explicit memory control, handled here with a custom allocator tracker in talloc.c.

Tokenizer Parser AST Evaluator Lexical Scoping Closures Custom GC-Style Cleanup

Background: Why Scheme, Why Interpreters, Why C?

Scheme is a minimalist Lisp dialect created by Gerald Jay Sussman and Guy L. Steele Jr. in the 1970s. It is used in programming languages courses because its syntax is compact and consistent, which makes the semantics easier to study. In an interpreter project, that means you can spend your energy on deep language concepts: syntax trees, environments, function application, and evaluation strategy.

Implementing this in C makes the learning sharper. C gives direct control over data representation and memory, but with that control comes responsibility. The project therefore pairs language implementation with memory discipline by routing allocations through talloc, then cleaning everything through tfree and texit.

This implementation follows a classic metacircular-style interpreter architecture in a low-level language. The source code demonstrates how high-level language ideas can be reduced to a small set of low-level mechanisms: tagged unions, linked structures, environment chains, recursive descent over expression trees, and controlled memory lifetimes.

Evaluation Pipeline

1) Tokenizer

Reads characters from input and emits token objects: numbers, symbols, booleans, strings, quotes, and parentheses.

2) Parser

Transforms the token stream into a nested AST using lists and quote wrapping logic.

3) Interpreter

Evaluates expressions with lexical scope, special forms, primitive operations, and closures.

4) Print

Prints each non-void result in Scheme-readable form, preserving list structure and values.

Input -> Tokenize -> Parse -> Eval -> Output 
(define x 10)
(define y 5)
(+ x y)
(if #t 42 0)

; output
15
42

Data Structures and Computational Concepts

1) Tagged union runtime values

The interpreter uses a single runtime object type (SchemeVal) with a type tag and a C union. This is a standard implementation pattern in dynamic language runtimes: one container type can represent numbers, symbols, strings, booleans, cons cells, closures, primitive function pointers, and control values like VOID_TYPE.

2) Lists and trees

In Scheme, code and data share list structure. Internally, parse trees are represented with cons cells rather than a separate AST node class hierarchy. That means expression trees are effectively list-based trees. The parser uses a stack of tokens and subtrees while tracking parenthesis depth, then constructs nested list structure when it encounters a close parenthesis.

This is a key Lisp idea: homoiconicity. The same pair/list data structure can represent both program source and runtime data. In this project, quoted forms reinforce that idea because 'expr is rewritten to (quote expr) before evaluation.

3) Environments as linked frame chains

Lexical scope is implemented with Frame objects. A frame stores local bindings and a pointer to a parent frame. Symbol lookup walks parent pointers outward until it finds a matching name. This gives static-scope behavior at runtime.

4) Closures and lambda calculus ideas

A lambda expression produces a closure object containing parameter names, function body, and the environment where the lambda was created. During application, a new frame is created whose parent is the closure's defining frame. That capture step is exactly what makes closures meaningful. Conceptually, this mirrors lambda calculus substitution, but implemented through environments and pointers.

5) Evaluation strategy

Function application is eager (applicative order): arguments are evaluated first with evalEach, then passed to apply. Special forms such as if, let, define, lambda, and quote have custom evaluation rules. This separation between ordinary application and special-form dispatch is central to interpreter design.

6) Higher-order programming

The primitive map shows higher-order behavior: functions are values, can be passed as arguments, and can be applied element-wise to lists. Combined with closures, this supports functional programming style with lexical capture.

7) Error discipline and arity checking

Many interpreter branches enforce structural invariants and arity constraints. Invalid expression shape, type mismatches, duplicate names, or wrong argument counts trigger evaluationError or syntax errors. This provides a defensive runtime boundary in a language without static typing.

How the Core Functions Work

Tokenizer functions

  • checkInitial and checkSubsequent encode valid symbol rules (Dybvig-style lexical constraints).
  • checkNumber identifies numeric digits while parsing integer and double tokens.
  • tokenize scans stdin, skipping whitespace/comments and constructing token lists.
  • displayTokens is useful for lexical debugging and token inspection.

Parser functions

  • addToParseTree handles open/close parentheses and subtree construction.
  • wrapAllQuotes rewrites quote shorthand so 'x becomes (quote x).
  • parse validates balanced structure and returns a complete AST list.
  • printTree prints tree forms back as readable Scheme syntax.

Interpreter functions

  • lookUpSymbol walks frame parents to implement lexical lookup.
  • eval is the central dispatcher over value tags and expression forms.
  • evalIf, evalDefine, evalLambda, evalLet implement special forms and argument validation.
  • apply handles both primitive function pointers and closure invocation.
  • evalEach evaluates argument lists before application.
  • bind installs primitive procedures in the global frame.
  • primitiveAdd, primitiveCar, primitiveCdr, primitiveCons, primitiveMap, primitiveNull provide baseline Scheme functionality.

Memory Management Spotlight: talloc as Safe Global Cleanup

In plain C, unmanaged malloc/free across many code paths can become error-prone. This interpreter centralizes memory tracking with a custom mechanism:

  1. talloc(size) allocates memory and records the returned pointer inside a global linked list of active allocations.
  2. tfree() walks that list, freeing each stored pointer and then freeing tracking nodes.
  3. texit(status) guarantees cleanup on fatal syntax/evaluation exits before process termination.

This is not a tracing garbage collector in the runtime-language sense, but it provides a project-level garbage-collection style safety net: all allocations made through talloc are reclaimed at once, preventing forgotten frees during parser/interpreter errors.

Compared to tracing garbage collection (such as mark-and-sweep), this approach does not discover live vs unreachable objects during execution. Instead, it records all allocations and frees them as a group at shutdown or error exit. So the model is deterministic bulk cleanup, not incremental runtime tracing. 

void *talloc(size_t size) {
    void *memory = malloc(size);
    ActiveList *node = malloc(sizeof(ActiveList));
    node->pointer = memory;
    node->next = ActiveListHead;
    ActiveListHead = node;
    return memory;
}

Data Representation and Lexical Scope

SchemeVal is a tagged union carrying integers, doubles, booleans, symbols, strings, cons cells, closures, and primitive function pointers. This design makes every runtime value explicit and inspectable.

Frame values form an environment chain. Every frame has a list of bindings and a parent pointer. When a lambda is created, the closure stores the environment it was defined in. During function application, parameters bind to arguments in a new frame whose parent is the closure's defining frame. That is lexical scoping in action.

Step-by-Step Example Through the Interpreter

(define square (lambda (x) (* x x)))
(square 4)
  • Tokenizer emits symbols, parentheses, and numbers.
  • Parser constructs nested list forms, preserving expression order.
  • define binds square to a closure from lambda.
  • On (square 4), apply creates a frame where x is bound to 4.
  • The body is evaluated in that frame and returns 16.
